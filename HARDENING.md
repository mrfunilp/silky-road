# Hardening

Security measures in the SilkyRoad stack, and what each one protects against.

## Container hardening

These measures do not stop an attacker from getting in. They limit what an attacker can do after gaining code execution inside a container.

### Read-only filesystem

`frontend`, `backend` and `db` run with `read_only: true` (`docker-compose.yml`). The only writable places are in-memory `tmpfs` mounts (emptied on restart) and the data volumes: `/tmp` everywhere, `/var/run/postgresql` for the database's socket, the database files in `db-data`, and the backend's pictures at `/data/images`.

- Served JavaScript cannot be modified, so no code can be injected to steal users' tokens
- The backend JAR cannot be replaced or patched
- The PostgreSQL binaries and configuration cannot be modified
- Nothing an attacker writes survives a restart
- Downloaded tools can only land in `/tmp`

### No root user

`frontend` runs as `nginx` (base image `nginxinc/nginx-unprivileged`), `backend` as `spring` (`USER spring` in `backend/Dockerfile`). Because non-root processes cannot bind ports below 1024, nginx listens on 8080.

- A compromised process cannot install packages, change system files or read other users' files
- Most container escape techniques require root inside the container

### Minimal network exposure

Only `frontend` publishes a port (`8081:8080`). The database and backend are reachable only inside the Compose network.

- PostgreSQL cannot be reached from the host or the internet
- The backend can only be reached through nginx, so every request it sees has passed nginx's limits and headers

### Multi-stage builds

Both Dockerfiles build in a separate stage. The final images contain only the build output (static files or JAR) and a runtime (nginx or JRE).

- No Node, npm, Maven, source code or build cache inside running containers

### Secrets from the environment

`POSTGRES_PASSWORD`, `APP_DB_PASSWORD` and `SILKYROAD_JWT_SECRET` come from `.env` (copied from `.env.example`).

- Compose refuses to start if any of them is missing
- The backend refuses to start if the JWT secret is shorter than 32 bytes (`JwtConfig`)
- `.env` is listed in `.gitignore` and `.dockerignore`, so no secrets end up in the Git repository or the images

## Application hardening

### XSS (cross-site scripting)

Angular escapes all values rendered with `{{ }}` and sanitizes URLs in `[src]` and `[href]`. The code never switches this protection off.

- All user text (item names, descriptions, comments, usernames) is rendered with `{{ }}`
- No `[innerHTML]`, `bypassSecurityTrust*`, `eval` or `document.write` in the frontend
- Only Angular event bindings like `(click)`, never inline `onclick` (rule in `CLAUDE.md`)
- Image URLs are generated by the server; clients cannot set them
- Uploads are limited to JPEG, PNG, GIF and WebP and are re-encoded; SVG and HTML are rejected
- Images are served with a fixed `Content-Type`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'`, so the browser never runs an uploaded file as a page or script
- A Content Security Policy on the app (see below) blocks injected scripts even if one of these rules is ever broken

### Content Security Policy

`nginx.conf` sends a `Content-Security-Policy` header with the app and its files:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;
connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'
```

- Only scripts from the app's own origin run; inline scripts, inline event handlers and `eval` are blocked
- The page can only talk to its own backend (`connect-src 'self'`), so injected code cannot send stolen tokens to another server
- `frame-ancestors 'none'` stops other sites from embedding the app in a frame (clickjacking)
- `base-uri` and `form-action` stop injected `<base>` or `<form>` tags from redirecting links or form data
- No plugins (`object-src 'none'`)
- Inline styles stay allowed (`'unsafe-inline'` for styles only), because Angular adds component styles as `<style>` tags
- Critical CSS inlining is turned off in `angular.json` (`inlineCritical: false`), because it loads the stylesheet with an inline `onload` handler that this policy would block

### Access control

Every endpoint except registration, login and `GET /api/images/*` needs a valid JWT (`SecurityConfig`). The acting user's ID always comes from the token, never from the request body.

- Only the owner of an item can edit or delete it and add or remove its pictures (`requireOwner` in `MarketplaceItemService`, otherwise 403)
- Only the author of a comment can delete it, and nobody can comment on their own item (`ItemCommentService`)
- Changing username, email or password only works on one's own account (`PUT /api/users/me`) and needs the current password
- Public profiles and item creators only expose ID and username; the email is returned only to the account owner

### SQL injection

All database access goes through Spring Data JPA, which runs every query as a prepared statement with bound parameters. User input never becomes part of the SQL text.

- Queries are derived from method names (e.g. `findByUsernameIgnoreCase`)
- The only hand-written query (`findByIdForUpdate`) is JPQL with a named parameter (`:id`)
- No native SQL, no `JdbcTemplate`, no string-built queries
- IDs are typed as `UUID`; invalid values are rejected before reaching the service layer
- Bean Validation (`@NotBlank`, `@Size`, `@Email`, `@DecimalMin`) on every request body

### Restricted database user

The backend runs its queries as `silkyroad_app`, a user that can only `SELECT`, `INSERT`, `UPDATE` and `DELETE` rows. Only Flyway connects as the owner `silkyroad` (a superuser in the Postgres image), and only to run migrations at startup. The user is created in `V2__app_user.sql` with its password from `APP_DB_PASSWORD`.

- `silkyroad_app` owns no tables, so it cannot drop or alter them
- It cannot create tables or other objects in the schema
- It cannot read or change Flyway's migration history
- It has no superuser rights, so it cannot run shell commands through Postgres (`COPY ... TO PROGRAM`)
- Tables added by later migrations get the same row rights automatically

Even if an attacker gets SQL access through the app (e.g. a future SQL injection bug), the database structure stays intact.

Flyway makes this possible: it creates the schema from versioned SQL files in `backend/src/main/resources/db/migration`, so the app no longer needs schema rights at runtime. Hibernate runs with `ddl-auto=validate` and only checks that the tables match the entities.

### Login rate limiting

`LoginRateLimiter` counts failed logins on `POST /api/users/login` in two token buckets (Bucket4j in a Caffeine cache). Once a bucket is empty, the request is rejected with **429 Too Many Requests** before the password is checked.

- Per username (case-insensitive): 5 failed attempts per 15 minutes
- Per client IP: 20 failed attempts per 15 minutes
- Buckets refill gradually, so a locked-out user can retry after a few minutes
- A successful login clears the username's bucket; only failures are counted
- Caches are capped at 100,000 entries and expire idle entries, so the limiter cannot exhaust memory
- The real client IP is read from nginx's `X-Forwarded-For` (`server.forward-headers-strategy=native`), not nginx's own address
- Failed logins always return "Invalid username or password.", whether the user exists or not

Protects against password guessing on one account, credential stuffing from one machine, and username enumeration via login. Passwords are also stored as BCrypt hashes, and changing account details requires the current password.

### Session lifetime (30 minutes)

After login the backend issues an HS256-signed JWT that expires **30 minutes** after issue (`silkyroad.jwt.ttl-seconds=1800`). There is no refresh token, so users log in again after 30 minutes.

- The backend is stateless (`SessionCreationPolicy.STATELESS`); every protected request needs a valid, unexpired token
- Tokens without a valid signature are rejected
- The frontend discards expired sessions on page load and logs out on any `401`
- The token is sent in the `Authorization` header, not as a cookie, so CSRF does not apply and is disabled

Protects against stolen tokens staying useful for long, and forgotten sessions on shared computers.

### Picture upload

Applies to `POST /api/items/{id}/images` and `GET /api/images/{name}` (`ImageStorageService`, `MarketplaceItemService`).

- Only JPEG, PNG, GIF and WebP, detected from the file content (not the file name or `Content-Type`)
- Every picture is re-encoded as JPEG or PNG, which removes hidden payloads and metadata such as GPS
- Max. 5 MB per file (Spring limit, 6 MB request limit in nginx), 8000 px per side, 3 per item
- Larger pictures are scaled down to 1600 px on the longest side before saving
- Random UUID file names chosen by the server; requested names must match that pattern, so no path traversal or overwriting
- Only the item's owner can upload or delete pictures, JWT required; the item row is locked during upload so the 3-picture limit cannot be raced
- Pictures of a deleted item are deleted from disk too
- Served with fixed `Content-Type`, `nosniff` and `Content-Security-Policy: default-src 'none'`
- Clients cannot set image URLs themselves
- The frontend checks type and size before uploading, but only for convenience; the server checks are what count

## Not hardened yet

- **Owner password in the backend:** Flyway runs inside the backend, so the backend still knows the owner password; running migrations in a separate one-off container would keep it out
- **Further security headers on the frontend:** besides the CSP, `nginx.conf` sets no `X-Content-Type-Options: nosniff` or `Referrer-Policy` for the app itself, and `server_tokens` is not turned off, so nginx reveals its version
- **Forwarded IP can be spoofed from private networks:** nginx appends to a client-sent `X-Forwarded-For` (`$proxy_add_x_forwarded_for`) instead of replacing it. Spring skips private addresses (10.x, 172.16–31.x, 192.168.x) as trusted proxies, so a client on such a network (e.g. the same LAN) can fake its IP and dodge the per-IP login limit; setting `X-Forwarded-For $remote_addr` in nginx would fix it
- **Registration reveals accounts and is not rate limited:** `POST /api/users` answers "That username is already taken." / "An account with that email already exists.", so usernames and emails can be enumerated there, and accounts can be created in bulk
- **Login timing:** for an unknown username the BCrypt check is skipped, so the response is measurably faster than for a wrong password; comparing against a dummy hash would hide that
- **Draft items are public:** `GET /api/items` and `GET /api/items/{id}` return items of every status, including other users' drafts and archived items
- **Token in `localStorage`:** any script that runs on the page (a future XSS bug, a compromised npm dependency, a malicious browser extension) can read it; an HttpOnly cookie would prevent that. The CSP limits where a stolen token can be sent, but not that it is read
- **Tokens cannot be revoked:** logout and password changes do not invalidate issued tokens before they expire
- **Further container options:** no `cap_drop`, `no-new-privileges` or memory/CPU limits
- **No HTTPS:** nginx serves plain HTTP; TLS (and then HSTS) must be added before going public
